## 判断を仰ぐこと

次のいずれかに該当する場合は、進める前に確認を取る。

**後から取り消せない変更**

ソフトウェアの内部にとどまらず、現実の世界に影響が残るものを含む。

- 稼働中の処理の挙動を変えるとき
- データを削除・上書きするとき
- 外部への送信や公開の条件を変えるとき(送信先、送信する内容、頻度、公開範囲)
- <プロジェクト固有の、後から取り消せない変更>

**作業を制約する側を変える変更**

取り決め、検査、権限のように、作業を縛る側に当たるものは、縛られる側の判断で変えない。

- 規定文書(<規定文書の一覧>)の規定を変える必要が生じたとき
- 規定文書どうしの記述が矛盾していると気づいたとき。どちらに合わせるかを独断で決めない
- 過去に決めたことを実質的に変えることになるとき
- テストやCIの検査を削除・スキップ・緩和するとき
- 権限が広がるとき、依存が増えるとき
- <プロジェクト固有の、制約を変える変更>

**費用や所要時間が大きく変わる変更**

- 費用が生じるとき
- 所要時間や費用が桁違いに変わる選択肢があるとき

いずれにも該当しない事柄は、自分で決めて進めるか、GitHub Issue に起票して先へ進む。
判断がつかない場合も Issue へ回す。

## 進め方

- オーナーと直接やり取りしているセッションが指揮役である。実装とレビューは
  タスクの難易度に応じてモデルを選び、サブエージェントに依頼する。
- 指示された範囲だけを実施する。頼まれていないことに手を広げない。
- 手を止めるのは、絶対ルールに抵触する場合と判断を仰ぐ場合だけとする。
- 不明点を推測で埋めない。実測するか、判断を仰ぐ。検証していない数値は報告しない。
- 作業中に気づいた課題は GitHub Issue に起票し、その場では手をつけない。
- 変更はプルリクエストとして提出し、必ず別のセッション（サブエージェント）のレビューを受ける。
  マージは人間が行う。オーナーが明示的に許可したプルリクエストだけは例外とする。
- リポジトリに入っている内容だけが事実である。push していない作業は存在しないものとして扱う。
