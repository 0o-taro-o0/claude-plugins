# 開発の手引き

作業に共通する事項をまとめる。判断の基準は `CLAUDE.md` にある。
作業ごとに異なる事項は、末尾の「作業別の手引き」から該当する1枚を読む。

## 作業の流れ

役割を3つに分け、成果物も指摘もすべてプルリクエスト上に残す。
セッションは使い捨てであるため、やり取りをプルリクエストに残しておけば、
そのセッションが終わった後も経緯をたどれる。

| 役割 | 担うこと |
|---|---|
| 指揮役 | 作業の範囲を定め、実装役とレビュー役へ依頼し、最後にオーナーへ報告する。実装は行わない |
| 実装役 | ブランチを作り、変更を加え、検証を通し、プルリクエストを作成する。指摘への対応も同じプルリクエスト上で行う |
| レビュー役 | プルリクエストを読み、指摘をコメントとして投稿する。自分では修正しない |

1. 指揮役が作業の範囲を定め、実装役へ依頼する(`/workflow:implementation-request`)
2. 実装役がプルリクエストを作成し、ラベルを `レビュー中` にする
3. 指揮役がレビュー役へ依頼する(`/workflow:review-request`)
4. レビュー役が指摘をプルリクエストへ投稿する(`/workflow:review-comment`)
5. 実装役が指摘の一つ一つに返信し、対応する。判断を要する指摘は保留にする
6. 4と5のやり取りは最大2往復までとし、解消しなかった指摘は保留としてオーナーへ回す
7. 指摘がすべて解消したらラベルを `マージ可` に変える。保留があれば `判断待ち` にする
8. 指揮役がオーナーへ報告する(`/workflow:work-report`)

レビュー役には、対象のプルリクエスト番号と観点だけを伝え、実装役による説明は渡さない。
変更の意図を先に読ませると、その説明と整合しているかを確かめるだけの形式的なレビューになる。

文書の修正であってもレビューを通す。

レビュー役は原則として1人とする。次に該当する変更に限り、2人へ依頼する。

- <レビュー役を2人にする条件。絶対ルールに関わる変更、取り返しのつかない削除を伴う変更 など>

## プルリクエストの状態

ラベルで示す。

| ラベル | 意味 |
|---|---|
| `実装中` | 実装役が作業している |
| `レビュー中` | レビュー役が読んでいる、または指摘に対応している |
| `判断待ち` | 保留した指摘があり、オーナーの判断を待っている |
| `マージ可` | 指摘がすべて解消し、検証も通っている |

## 課題の起票

作業中に気づいた課題は、その場では手をつけず、GitHub Issue に起票して先へ進む。

- 課題は Issue テンプレート「課題」で起票する。概要・詳細・方針を埋め、
  判断に必要な事実は本文に書き写す
- オーナーへの判断依頼は `/workflow:decision-request` の書式で起票する
- 残っている課題と進み具合は、Issue の open/close で追う
- 起票した課題への着手は、指揮役が範囲を定めてから行う

## 常駐指揮役モード

オーナーの代行として、残っている課題を横断的に消化するセッションの動き方である。

- オーナーが明示的に任せたセッションだけが、このモードで動く。それ以外のセッションは
  「作業の流れ」の役割分担に従う。
- 課題のうち `CLAUDE.md`「判断を仰ぐこと」に該当しないものは、着手順を自分で決めて
  消化してよい。該当するものは判断依頼を起票し、手を止めずに次の課題へ進む。
- 指揮役はコードも文書も自分で読まない・書かない。調査・実装・レビューのすべてを
  使い捨ての別セッションへ委任し、結論だけを受け取る。1タスクにつき1セッションとする。
- 成果物は必ず実装役から別セッションのレビュー役へ通し、指摘が収束したときだけ
  指揮役がラベルを変える。指揮役は承認者ではなく交通整理役であり、レビューの結論を
  自分で上書きしない。
- やり取りはすべてプルリクエストと Issue に残す。セッションが消えても経緯をたどれる
  ようにするためである。
- 節目の報告は「マージ待ち」「判断待ち」「実行待ち(オーナーにしかできない作業)」の
  3分類で行う。
- 委任先のセッションは必ず新規の worktree を作って作業し、main 本体や他のセッションの
  worktree に触れない。

## コミットとプルリクエスト

- コミットメッセージは Conventional Commits に従い、`<種類>(<範囲>): <要約>` の形で書く。
  要約は日本語1行とする。種類は `feat` `fix` `docs` `refactor` `perf` `test` `ci` `chore`
  から選び、範囲は <コミット範囲の候補> のように変更した箇所を入れる。
  範囲を絞れない場合は省いてよい。
- 分離可能な変更はコミットを分ける。片方だけを採用できるようにするためである。
- プルリクエスト本文には、変更した内容と検証した結果を書く。文書本体から除いた経緯や
  理由は、プルリクエスト本文に書いてよい(書く場所である)。コミットメッセージには
  経緯を書かない。
- マージは人間が行う。ただし、オーナーから特定のプルリクエストのマージを
  明示的に許可された場合は、マージしてよい。

## 文書作成

### 構成

作業に関係のない情報を読まずに済むよう、文書を4層に分ける。
上の層ほど読む人が多いため、上の層は薄く保つ。

| 層 | 文書 | 内容 | 読むとき |
|---|---|---|---|
| 1 | `CLAUDE.md` | 判断の基準 | 全セッションが最初に読む |
| 2 | `CONTRIBUTING.md` | 作業に共通する手順 | 手を動かす前に読む |
| 3 | `docs/guides/` | 作業ごとの手順 | 自分の作業に当たる1枚だけを読む |
| 4 | <基準文書> | 設計と規定の全文 | 必要な箇所だけを引く |

**上の層に、下の層の内容や基準文書への参照を書かない。**
第1層に基準文書の節への参照を書けば、全セッションがその文書を開く。
基準文書の分量が増えるほど、これを繰り返すと、どのセッションも自分の作業と関係のない
規定を読むことに時間を使う。参照は、それを必要とする層に置く。

- 文書を増やさない。既にある文書への追記で足りるなら、新しいファイルは作らない。
- 決めたことと理由は、決定の記録(<決定の記録の置き場所と形式>)に日付を付けて
  1件だけ記す。理由を複数の場所に散らさない。
- 実装状態(「未着手」「後続PRで行う」)を文書に書かない。
  何が残っていて何が終わったかは、GitHub Issue の open/close で追う。

### 書き方

- 見出しは名詞句で揃える。内部の呼び名や記号をそのまま見出しにしない。
- 判断や報告を求める文章は、参照先を開かなくても意味が通るように書く。
  必要な事実は本文に書き写す。
- 基準文書に書く事実は1箇所に置き、他からは参照する。同じ事実を複数の基準文書へ書き写さない。
- 修正は、過去の経緯や修正前の状態を匂わせる記述(「以前は〜だったが」「(◯◯を含む)」の
  ような、修正前を知らなければ書かない文)を残さず、単体で読んで自然な、元からそうで
  あったかのような文にする。経緯や理由は文書本体ではなく、決定の記録とプルリクエスト
  本文に置く。
- コードのコメントには、なぜそうしたのかだけを書く。コードを読めば分かることは書かない。
- <日本語校正の設定。使用する校正ツールと設定ファイル、有効にするルール、抑止の規約>

## 導入手順

プラグイン workflow の雛形からこの体制を導入するときに、一度だけ行う。

1. 雛形2枚(`CLAUDE.md`、本ファイル)をプラグインの `templates/` からプロジェクトルートへ複写し、`<>` の欄を埋める
2. Issue テンプレート2種(`templates/ISSUE_TEMPLATE/task.md`、同 `decision-request.md`)を `.github/ISSUE_TEMPLATE/` へ複写する
3. プルリクエストの状態を示すラベル4種を作る

ラベルは次のコマンドで作る。

    gh label create 実装中 --color FBCA04 --description "実装役が作業している"
    gh label create レビュー中 --color 1D76DB --description "レビュー役が読んでいる、または指摘に対応している"
    gh label create 判断待ち --color D93F0B --description "保留した指摘があり、オーナーの判断を待っている"
    gh label create マージ可 --color 0E8A16 --description "指摘がすべて解消し、検証も通っている"

ラベルの色は、このコマンドの `--color` が唯一の定義箇所である。複数のリポジトリで
色を揃える場合も、この手順の色をそのまま使う。既存のラベルと色が異なる場合は
`gh label edit <ラベル名> --color <色>` で合わせる。
