# 開発の手引き

作業に共通する事項をまとめる。判断の基準は `CLAUDE.md` にある。
作業ごとに異なる事項は、末尾の「作業別の手引き」から該当する1枚を読む。

## 作業の流れ

役割を3つに分け、成果物も指摘もすべてプルリクエスト上に残す。
セッションは使い捨てであるため、やり取りをプルリクエストに残しておけば、
そのセッションが終わった後も経緯をたどれる。

| 役割 | 担うこと |
|---|---|
| 指揮役 | 作業の範囲を定め、実装役とレビュー役へ依頼し、最後にオーナーへ報告する。実装は行わない |
| 実装役 | ブランチを作り、変更を加え、検証を通し、プルリクエストを作成する。指摘への対応も同じプルリクエスト上で行う |
| レビュー役 | プルリクエストを読み、指摘をコメントとして投稿する。自分では修正しない |

1. 指揮役が作業の範囲を定め、実装役へ依頼する(`/workflow:implementation-request`)
2. 実装役がプルリクエストを作成し、ラベルを `レビュー中` にする
3. 指揮役がレビュー役へ依頼する(`/workflow:review-request`)
4. レビュー役が指摘をプルリクエストへ投稿する(`/workflow:review-comment`)
5. 実装役が指摘の一つ一つに返信し、対応する。判断を要する指摘は対応を保留し、
   判断依頼 Issue を起票して(`/workflow:decision-request`)番号をプルリクエストへ
   返信し、ラベルを `保留` にする
6. 4と5のやり取りは最大2往復までとし、解消しなかった指摘も5と同じ手順で判断依頼
   Issue へ回す
7. 裁定が出たら実装役が対応を再開し、ラベルを `レビュー中` へ戻す。指摘がすべて
   解消したらラベルを `マージ可` に変える
8. 指揮役がオーナーへ報告する(`/workflow:work-report`)

レビュー役には、対象のプルリクエスト番号と観点だけを伝え、実装役による説明は渡さない。
変更の意図を先に読ませると、その説明と整合しているかを確かめるだけの形式的なレビューになる。

文書の修正であってもレビューを通す。

レビュー役は原則として1人とする。次に該当する変更に限り、2人へ依頼する。

- <レビュー役を2人にする条件。絶対ルールに関わる変更、取り返しのつかない削除を伴う変更 など>

## ラベル

ラベルはプルリクエストと Issue で分け、共用しない。
プルリクエストのラベルは状態を、Issue のラベルは種別を表す。

プルリクエストには状態を1つ付ける。

| ラベル | 意味 |
|---|---|
| `実装中` | 実装役が作業している |
| `レビュー中` | レビュー役が読んでいる、または指摘に対応している |
| `保留` | 保留した指摘があり、対応する判断依頼 Issue の裁定を待っている。裁定が出たら実装役が対応を再開し `レビュー中` へ戻す |
| `マージ可` | 指摘がすべて解消し、検証も通っている |

Issue には種別を付ける。

| ラベル | 意味 |
|---|---|
| `課題` | 作業中に気づいた課題 |
| `判断依頼` | オーナーへ判断を求める |

## 課題の起票

作業中に気づいた課題は、その場では手をつけず、GitHub Issue に起票して先へ進む。

- Issue テンプレート「課題」で起票する。ラベル「課題」が自動で付く
- 判断に必要な事実は本文に書き写す
- コマンドから起票する場合はテンプレートが適用されないため、テンプレートと同じ
  見出し構成で本文を書き、`--label 課題` を付ける
- 残っている課題と進み具合は、Issue の open/close で追う
- 起票した課題への着手は、指揮役が範囲を定めてから行う

## 判断依頼

オーナーの判断を要する事柄は、`/workflow:decision-request` の書式で GitHub Issue に
起票する。起票からクローズまでの運用は、その書式に定める。
判断を求める文章をプルリクエスト本文・コメントに書かない。プルリクエストには
起票した Issue 番号の参照だけを書く。

## コミットとプルリクエスト

- コミットメッセージは Conventional Commits に従い、`<種類>(<範囲>): <要約>` の形で書く。
  要約は日本語1行とする。種類は `feat` `fix` `docs` `refactor` `perf` `test` `ci` `chore`
  から選び、範囲は <コミット範囲の候補> のように変更した箇所を入れる。
  範囲を絞れない場合は省いてよい。
- 分離可能な変更はコミットを分ける。片方だけを採用できるようにするためである。
- 設計の変更は、実装とは別のプルリクエストに分ける。
- プルリクエスト本文には、変更した内容と検証した結果を書く。文書本体から除いた経緯や
  理由は、プルリクエスト本文に書いてよい(書く場所である)。コミットメッセージには
  経緯を書かない。
- マージは人間が行う。ただし、オーナーから特定のプルリクエストのマージを
  明示的に許可された場合は、マージしてよい。

## 文書作成

### 構成

作業に関係のない情報を読まずに済むよう、文書を4層に分ける。
上の層ほど読む人が多いため、上の層は薄く保つ。

| 層 | 文書 | 内容 | 読むとき |
|---|---|---|---|
| 1 | `CLAUDE.md` | 判断の基準 | 全セッションが最初に読む |
| 2 | `CONTRIBUTING.md` | 作業に共通する手順 | 手を動かす前に読む |
| 3 | `docs/guides/`・`docs/runbooks/` | 作業ごとの手順 | 自分の作業に当たる1枚だけを読む |
| 4 | <規定文書> | 設計と規定の全文 | 必要な箇所だけを引く |

**上の層に、下の層の内容や規定文書への参照を書かない。**
第1層に規定文書の節への参照を書けば、全セッションがその文書を開く。
規定文書の分量が増えるほど、これを繰り返すと、どのセッションも自分の作業と関係のない
規定を読むことに時間を使う。参照は、それを必要とする層に置く。

- 文書を増やさない。既にある文書への追記で足りるなら、新しいファイルは作らない。
- 規定文書には現在形の規定だけを書く。実装状態(「未着手」「後続PRで行う」)は書かず、
  何が残っていて何が終わったかは GitHub Issue の open/close で追う。
- 決めたことと理由の記録は、判断依頼の Issue を正とする。専用の決定ログは持たず、
  クローズ済みの判断依頼 Issue の集合が決定の記録になる。理由を複数の場所に散らさない。
- 手順は削除せず、作業単位のファイルへ分ける。`docs/guides/` は分野名、`docs/runbooks/` は
  作業名で命名し、ファイル名だけで規則か手順かが分かるようにする。

### 書き方

- 文章は簡潔で正確な日本語で書く。翻訳調の言い回しを避け、
  熟語で簡潔に書ける箇所を冗長な言い回しにしない。
- 見出しは名詞句で揃える。内部の呼び名や記号をそのまま見出しにしない。
- 判断や報告を求める文章は、参照先を開かなくても意味が通るように書く。
  必要な事実は本文に書き写す。これは報告と依頼の書式に限った規定であり、
  規定文書には適用しない。
- 規定文書に書く事実は1箇所に置き、他からは参照する。同じ事実を複数の規定文書へ書き写さない。
- 文書を修正するとき、過去の誤りや修正前の状態を匂わせる記述を残してはならない。
  その瞬間に単体で読んで自然な、元からそうであったかのような文にする。
  「A だけが対象外。それ以外(B を含む)は対象とする」の「(B を含む)」は過去の誤記への
  言い訳であり、元からそう書くなら「A だけが対象外とする」の一文で足りる。
  経緯や理由は文書本体ではなく、判断依頼の Issue とプルリクエスト本文に置く。
- コードのコメントには、なぜそうしたのかだけを書く。コードを読めば分かることは書かない。
