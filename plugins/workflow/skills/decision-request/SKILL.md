# 判断依頼

オーナーへ判断を求めるときに使う。

```markdown
## 該当

<CLAUDE.md「判断を仰ぐこと」のどれに当たるか>

## 状況

<前提知識なしで読める説明。3〜5行。
関連する数値、ファイル名、エラーの実物は、参照ではなくここに書き写す>

## 判断を要する理由

<こちらで決められない理由。1〜2行>

## 選択肢

- [ ] A. <案> — <選んだ場合に何が起きるか。所要時間や費用も書く>
- [ ] B. <案> — <同上>

## 推奨

<どれを推すか。理由を1〜2行>

## 放置した場合の影響

<期限があるかどうか。なければ「特に問題は生じない」と書く>

## 判断結果の記録先

<判断が出たら、どこへ反映するか。規定文書やプルリクエストなど。判断の記録はこの Issue に残る>
```

## 起票

書式を埋めたら、GitHub Issue として起票する。起票した Issue を正とし、判断の結果も
Issue に残す。Web から起票する場合は Issue テンプレート「判断依頼」を使う(ラベル
「判断依頼」が自動で付く)。コマンドから起票する場合はテンプレートが適用されないため、
テンプレートと同じ見出し構成の Markdown で本文を書き、ラベルを付ける。

    gh issue create --title "判断依頼: <題名>" --label 判断依頼 --body-file <書式を埋めたファイル>

判断依頼は1件につき1つの Issue とする。判断が出たら、判断結果の記録先へ反映してから
Issue をクローズし、クローズコメントに判断の内容と反映先を書く。

## 注意事項

- 判断を求める文章をプルリクエスト本文・コメントに書かない。この書式で Issue を
  起票し、プルリクエストには番号の参照だけを書く。
- プルリクエストがこの判断でブロックされる場合は、プルリクエストのラベルを `保留` に
  して Issue 番号を返信し、Issue にもプルリクエスト番号を書いて相互にリンクする。
- 作業報告のなかで判断を求める場合は、起票した Issue の番号と題名を
  作業報告の「判断を仰ぎたいこと」に書く。
- 参照先を開かなくても意味が通るように書く。
- 軽重を混ぜない。重い判断と軽い判断を同じ一覧に並べない。
- 「判断を仰ぐこと」に該当しないものは、自分で決めるか GitHub Issue へ回す。
