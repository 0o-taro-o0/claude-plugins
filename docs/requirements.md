# 要件定義書:個人開発のための Claude 共通設定(ドラフト v0.3)

> 状態:ドラフト。レビュー・赤入れ待ち。
> 目的:何を作るかを決める前に「何に困っていて、何を Claude に任せ、何を人間が握るか」を確定する。
> 構成:骨格は、実運用で機能することを確認済みの運用モデル(3 節)である。運用モデルでカバーされない事項は、未実証の追加要件(4 節)として区別する。どの記述が実証済みでどれが未実証かは、この 2 節の別で示す。

## 1. 現状

- 複数リポジトリを個人開発している。スタックは AWS / Python / Node.js / Go(Go は自分では書かない=読解支援の重要度が高い)。
- Claude Code は基本 Web 版。ローカル環境や AWS 認証情報が必要な作業のみローカル CLI。
- 開発の進め方はセッション分業型。人間と直接やり取りする指揮役セッションが作業の範囲を定め、実装とレビューを別のセッションへ依頼し、AI 同士が PR 上で作業を進める。人間は「判断」と「マージ」を担う。
- この分業は別プロジェクトでの実運用を経ており、機能することを確認した運用のかたちを 3 節の運用モデルとしてまとめている。本件は、この運用モデルをどのリポジトリでも同じように再現できる共通設定として整備するものである。

## 2. 解決したい課題

実際に困った実例の記録である。3 節・4 節の要件は、この一覧の課題番号(P)へ対応づける。

| # | 課題 | 現状の症状 |
|---|------|-----------|
| P1 | 規約が実行時に守られない | TDD で開発すると規約に書いてあるのに、コード先行・テスト後書きになる |
| P2 | 定型セッションの段取りを毎回手打ちしている | コーディング/レビューセッションの手順(PR 作成 → 購読 → 対応ループ等)を毎回指示している |
| P3 | AI が人間の権限を越えることがある | たまに勝手にマージされる。マージは人間の判断にしたい |
| P4 | 人間判断の漏れを検証できない | 人間が判断すべき事項を AI 同士で勝手に決めて進めていないか、不安が残る |
| P5 | 判断を求められたときの説明が不親切 | コードやドキュメントを自分で探して参照しないと判断できない。毎回質問して説明させるのが面倒 |
| P6 | 理解が浅いまま着手する | 中途半端な理解のまま開発を始める。リポジトリ全体を確認せず一部だけの認識でコードを書いてきて、指摘する手間が発生する。求めてもいないファイルを作り始める |
| P7 | ドキュメントの形式がバラバラ | ものによって書き方・構成が違い、一貫性がない |
| P8 | 途中指示がドキュメントに「継ぎ足し」で残る | 開発途中に出した指示がそのまま追記され、木の節のように目立つ形で残る。本来はきれいな一貫した品質のドキュメントに織り込まれてほしい |
| P9 | Issue・PR の形式がバラバラ | 書かれ方が毎回違うので、読むたびに構造を把握し直す認知負荷がかかる |
| P10 | コード内の命名がばらつく・実態を表さない | 変数などの命名が実行ごとにばらつく。また「その名前ではコードの実態を表さないだろう」という命名をすることがある |
| P11 | AWS リソースの命名・タグに規則がない | リソース名やタグの付け方が統一されておらず、管理しづらい |
| P12 | 用語が定義されておらず、勝手に言い換えられる | 今まで使っていた用語を突然別の言い方で表現してくるので、同じものを指しているのか分からなくなる |
| P13 | AI 生成特有の不自然な日本語 | 突然、不自然な言い回しや使い慣れない比喩を使った文書を出してくる。自然な日本語で書くことを徹底したい。見出しに文章を書くのも嫌(日本語ではしない) |
| P14 | 図を入れる基準がない | アーキテクチャ・概念・AWS 構成などは図が適する場面で文章だけで説明される。かといって全てのケースで図が欲しいわけでもなく、入れる/入れないの基準がない |
| P15 | 表の形式が不統一 | 表形式で情報を並べるときの書き方にルールがなく、統一性がない |
| P16 | 記法の使い分けができていない | GitHub 上の文書(PR・Issue・コメント)では GitHub の拡張記法を活かせるのに使わない。一方でリポジトリに格納する文書に環境依存の記法を使われても困る |
| P17 | AI の対応コメントにルールがない | レビュー指摘などに AI が対応したとき、どんなコメントをどんな形式で残すかが決まっていない |
| P18 | 確認・調査が思いつきベース | 「問題となりうる箇所がないか確認して」と頼むと、仕組み的に網羅せず、思いついた一部だけを挙げてくる。何をどこまで調べたのかも分からない |
| P19 | 不具合対応が対症療法で終わる | 目の前の症状を直して終わりになりがち。根本原因の掘り下げ(なぜなぜ分析)や、同様の不具合が他に埋め込まれていないかの横展開確認をしてほしい |
| P20 | コード内コメントに規律がない | 何をコメントに書き、何を書かないかが決まっておらず、書き方・量がばらつく |
| P21 | 課題管理が二重になる | 作業中に気づいた課題の置き場が定まっておらず、リポジトリ内の課題台帳(CSV)と GitHub Issue の二重管理が実運用で発生した |

## 3. 実証済みの運用モデル

別プロジェクトでの実運用により機能することを確認済みの運用を、特定プロジェクト固有の内容を除いて汎用化し、本件の骨格とする。3 節の要件は「導入するかどうか」ではなく、**どのリポジトリでも同じように再現できるようにすること**である。

### 3.1 役割分担と人間の専権事項(→ P3, P4)

役割を 3 つに分け、それぞれ別のセッションが担う。

| 役割 | 担うこと |
|---|---|
| 指揮役 | 人間と直接やり取りする窓口。作業の範囲を定め、実装役とレビュー役へ依頼し、最後に人間へ報告する。自分では実装しない |
| 実装役 | ブランチを作り、変更を加え、検証を通し、PR を作成する。指摘への対応も同じ PR 上で行う |
| レビュー役 | PR を読み、指摘をコメントとして投稿する。自分では修正しない |

人間(オーナー)だけが行うこと:

1. **マージ**(およびリリースのタグ付け)
2. **機能の仕様・仕組みの最終決定**(AI は選択肢と論点を出し、議論相手にはなるが、決定はしない)
3. **リリース前の実動作確認**(AI は確認手順とチェックリストを用意する)

- AI はこれらを代行しない。指示が曖昧でも勝手に踏み込まず確認を取る。
- 自分が書いたものを自分で承認しない。PR には必ず別のセッションのレビューを受ける。
- 指示だけに頼らず技術的にも強制する:マージ系操作の権限拒否設定、GitHub ブランチ保護
  (人間の approve 必須)を併用する。ブランチ保護は現在未導入であり、
  **本件のセットアップの一部として各リポジトリへ導入する**
  (導入手順をドキュメント化し、新規リポジトリ立ち上げ手順にも含める)。

### 3.2 作業の流れと PR 中心の原則(→ P3, P9, P17)

セッションは使い捨てで保存されないため、成果物も指摘もやり取りも、すべて PR 上に残す。
**リポジトリ(GitHub 上)に残っている内容だけが事実**であり、push していない作業は
存在しないものとして扱う。

1. 指揮役が作業の範囲を定め、実装役へ依頼する(書式:実装依頼)
2. 実装役が PR を作成し、ラベルを「レビュー中」にする
3. 指揮役がレビュー役へ依頼する(書式:レビュー依頼)
4. レビュー役が指摘を PR へ投稿する(書式:指摘)
5. 実装役が指摘 1 件ごとに返信し、対応する。判断を要する指摘は保留にする
6. 4 と 5 のやり取りは最大 2 往復までとし、解消しなかった指摘は保留として人間へ回す
   (AI 同士の押し問答で時間を消費させない)
7. 指摘がすべて解消したらラベルを「マージ可」に変える。保留があれば「判断待ち」にする
8. 指揮役が人間へ報告する(書式:作業報告)

この流れに付随する規律:

- 指示された範囲だけを実施する。頼まれていないことに手を広げない。
  範囲外の課題は Issue へ起票して先へ進む(3.6)。
- 不明点を推測で埋めない。実測するか、判断を仰ぐ(3.4)。検証していない数値は報告しない。
- 文書の修正であってもレビューを通す。取り決め(設計・規約)の変更は、
  実装とは別の PR に分ける。
- レビュー役には対象 PR 番号と観点だけを渡し、実装役による説明は渡さない
  (変更の意図を先に読ませると、その説明と整合しているかを確かめるだけの
  形式的なレビューになる)。
- レビュー役は原則 1 セッションとし、後から取り消せない変更(3.4 の分類 1)に関わる
  PR に限り 2 セッションへ依頼する。
- 「マージ可」の条件は、指摘がすべて解消し、テスト・lint・型チェック等の検証
  (CI と同じもの)が通っていること。
- コミットメッセージは Conventional Commits に従い、要約は日本語 1 行とする。
  分離可能な変更はコミットを分ける(片方だけを採用できるようにする)。
  PR 本文には変更した内容と検証した結果だけを書き、検討の経緯や見送った案は書かない。
- 指摘への対応コメント:対応した場合は何をどう変えたか(1〜2 行)+
  対応コミットへの参照を書き、「修正しました」だけの中身のない返信を禁止する。
  対応しない場合は必ず理由を書く(見送りの判断根拠、代替案)。無言で放置しない。
  判断を人間に委ねる場合は判断依頼(3.5)の形式に従う。
  指摘スレッドの解決(resolve)を誰がするか(対応した AI か、確認した人間か)は
  次工程で定める。

### 3.3 ラベルによる状態管理(→ P9)

PR の状態はラベルで示し、どのリポジトリでも同じ 4 種を使う。

| ラベル | 意味 |
|---|---|
| 実装中 | 実装役が作業している |
| レビュー中 | レビュー役が読んでいる、または指摘に対応している |
| 判断待ち | 保留した指摘があり、人間の判断を待っている |
| マージ可 | 指摘がすべて解消し、検証も通っている |

### 3.4 人間の判断を仰ぐ 3 分類(→ P4)

作業中に人間の判断を仰ぐ基準を次の 3 分類で定める。

1. **後から取り消せない変更**:データの削除・上書き、稼働中の処理の挙動変更、
   外部への送信・公開の条件の変更など
2. **取り決めを変える変更**:合意済みの設計・規約・既決事項を実質的に変えることになる場合、
   規定どうしの矛盾に気づいた場合(どちらに合わせるかを独断で決めない)
3. **歯止めを緩める変更、費用や権限が増える変更**:テスト・CI の検査の削除・スキップ・緩和、
   費用の発生、権限や依存の拡大など

いずれにも該当しない事柄は、AI が自分で決めて進めるか、Issue へ起票して(3.6)先へ進む。
判断がつかない場合も Issue へ回す。「迷ったら全部聞く」でも「全部自分で決める」でもなく、
この 3 分類との照合で機械的に振り分ける。

### 3.5 定型書式 5 種(→ P5, P9)

依頼・指摘・報告はすべて次の 5 書式で行う。**「AI からの出力はすべて定型フォーマットで
受け取る」を横断原則**とし、見慣れた形に統一することで読む側(人間)の認知負荷を下げる。
書式の定義は本節に一本化し、他の節からは本節を参照する。

| 書式 | 使う場面 | 主な項目 |
|---|---|---|
| 実装依頼 | 指揮役 → 実装役 | 目的/範囲/範囲外/完了条件/参考 |
| レビュー依頼 | 指揮役 → レビュー役 | 対象 PR 番号/観点 |
| 指摘 | レビュー役 → PR | 区分/問題/根拠 |
| 判断依頼 | AI → 人間 | 該当分類/状況/選択肢/推奨/放置した場合 |
| 作業報告 | 指揮役 → 人間 | 結論/行ったこと/成果物/検証結果/指摘と対応/判断を仰ぎたいこと |

書式ごとの規律:

- **実装依頼**:範囲外を必ず書く(書かないと周辺の改善にまで手が広がる)。
  参考には場所を示すだけでなく、判断に必要な事実を依頼文そのものに書き写す。
- **レビュー依頼**:対象 PR 番号と観点だけを渡す(3.2 の規律に従う)。
- **指摘**:1 件ずつ別のコメントに分け、次の区分を付ける。推測で指摘せず、
  実際に確かめた内容を根拠として書く。実装役の説明ではなく、変更そのものを見て判断する。
  - **差し戻し**:明確な不具合・検証の不備・3.4 の判断基準に該当するもの。
    対応するまでマージしない
  - **推奨**:直したほうがよいが、直さなくても動くもの。対応の要否は実装役が判断し、
    直さない場合は Issue へ起票する(3.6)
  - **任意**:好みの範囲にとどまるもの。対応しなくてよい
- **判断依頼**:その場で読むだけで判断できる自己完結の形で書く。含める項目:
  3 分類(3.4)のどれに該当するか/前提知識なしで読める状況説明(数値・ファイル名・
  エラーの実物は、参照ではなく本文に書き写す)/選択肢と、それぞれを選んだ場合に
  何が起きるか(所要時間・費用を含む)/推奨案と理由/放置した場合に何が起きるか
  (期限の有無)。3 分類に該当しないものは判断依頼にせず、自分で決めるか Issue へ回す。
  重い判断と軽い判断を同じ一覧に並べない。
- **作業報告**:1 行目に結論(人間が次に何をすればよいか)を書く。判断を要する件があれば、
  別のメッセージに切り出さず、報告の中に判断依頼の項目をそのまま埋め込む
  (報告と判断材料を 1 か所で読めるようにする)。
  **人間判断に委ねた事項/AI 側で判断した事項の一覧**を含め、勝手に決めて進めていないかを
  人間が監査できるようにする。この一覧はセッションの出力で終わらせず、
  PR(説明欄またはコメント)に記録として残す(3.2 の原則:残っている内容だけが事実)。

### 3.6 課題と判断依頼の GitHub Issue 一本化(→ P21)

- 作業中に気づいた範囲外の課題は、その場で手をつけず GitHub Issue へ起票して先へ進む。
  リポジトリ内に CSV 等の課題台帳を持たない(台帳と Issue の二重管理が実運用で発生した。
  同じ課題を 2 か所に書く手間と、どちらが最新か分からなくなる問題を、
  置き場を 1 つにすることで断つ)。
- 人間の判断を要する事項も GitHub Issue へ起票する。**Issue を正とし、
  作業報告への埋め込み(3.5)は読みやすさのための写し**とする。
  報告文中にしか存在しない判断依頼は、セッションが終わった時点で忘れられうるうえ、
  裁定待ちの全量を一覧できず、裁定の結果も証跡として残らない。
  Issue に起票すれば、裁定待ちは Issue の一覧で追跡でき、裁定後のクローズが証跡になる。
- 裁定の記録先と、クローズの条件(誰がいつ閉じるか)も運用として定める(具体化は次工程)。
- 課題と裁定待ちという「人間が追うべきもの」の置き場を GitHub Issue の 1 か所にする。
  「リポジトリに残っている内容だけが事実」(3.2)の原則とも整合する。

### 3.7 文書の 4 層構造(→ P7)

作業に関係のない情報を読まずに済むよう、リポジトリの文書を 4 層に分ける。

| 層 | 内容 | 読むとき |
|---|---|---|
| 1 | 判断の基準 | 全セッションが最初に読む |
| 2 | 作業に共通する手順 | 手を動かす前に読む |
| 3 | 作業別の手順 | 自分の作業に当たる 1 枚だけを読む |
| 4 | 正本(設計・規定の全文) | 必要な箇所だけを引く |

- 上の層ほど読む機会が多いため、薄く保つ。**上の層に下の層の内容や正本への参照を書かない**。
  上の層に正本への参照を書くと、全セッションが正本を開くことになり、
  自分の作業と関係のない規定を読むことに時間を使う。参照は、それを必要とする層に置く。
- 文書を増やさない。既にある文書への追記で足りるなら、新しいファイルは作らない。
- 正本に書く事実は 1 箇所に置き、他からは参照する。同じ事実を複数の正本へ書き写さない。
- 実装状態(「未着手」「後続 PR で対応」)を正本に書かない。
  状態を持つのは課題管理(3.6 の GitHub Issue)だけとする。

## 4. 追加要件(未実証)

運用モデルと直交し、2 節の課題への対処として残す価値があると判断した要件である。
いずれも実運用での機能確認を経ていないため、運用モデルと同格には扱わない。
導入時に個別に検証し、有効と確認できたものから運用モデルへ組み入れる。

### 4.1 TDD の手順化(→ P1)

- 「規約に書いておく」だけでは守られないことが実証済み。コーディング手順そのものに
  「(1) まず失敗するテストを書く →(2) 失敗することを確認 →(3) 実装 →(4) 通過を確認」
  を明示的なステップとして組み込む。
- 作業報告(3.5)に「テストを先に書き、実装前に失敗を確認したか」を必須項目として含めさせる。

### 4.2 着手前の理解確認(→ P6)

コードを書き始める前に、次を必ず行う:

1. **リポジトリ全体の把握**:関連コードだけでなく、全体構造・既存の類似実装・規約を確認する。
   一部だけ読んで書き始めない。
2. **理解の提示**:タスクの理解・影響範囲・進め方を短く提示し、認識がずれていれば
   ここで直せるようにする。理解に穴があるなら着手前に質問する。
3. **成果物の限定**:求められた成果物以外のファイルを勝手に作らない
   (「ついでに」の README・サンプル・スクリプト生成を禁止)。

### 4.3 コード内の命名とコメント(→ P10, P20)

命名は、コードごとに中身が違う以上、完全な統一ルールは作れない。そこで 2 層で対応する:

- **共通の命名原則**(共通設定側):名前は役割・内容を表す(処理の実態と食い違う名前を
  付けない)。boolean は `is/has/can` 等、関数は動詞句、定数・環境変数は大文字スネーク等の
  一般慣習に従う。**新しい名前を導入する前に、既存コードで同じ概念に使われている語を探し、
  それに合わせる**(同じ概念に別の語を増やさない)。
- **リポジトリ固有の語彙**(各リポの CLAUDE.md):そのプロジェクトのドメイン用語集
  (この概念はこの単語で呼ぶ)を書き、命名時に参照させる。
- 「命名が実態を表しているか」をレビュー役(3.1)の明示的な観点に含める。

コード内コメントの規律(詳細は次工程で確定。候補):

- コードを読めば分かることを書かない(処理の逐語説明の禁止)。
  書くのは**コードから読み取れないこと**:意図、制約、そうした理由、既知の落とし穴。
- 変更の経緯・作業説明(「〜を修正」「レビュー指摘対応」等)をコードに残さない。
  経緯は git・PR が持つ(4.6 の「履歴は git に任せる」と同じ原則)。
- 公開 API・関数のドキュメントコメントは、言語ごとの標準慣習
  (docstring、JSDoc、godoc 等)に従う。コメントの言語(日本語/英語)の方針も定める。

### 4.4 用語の定義と言い換えの禁止(→ P12)

- **同じ概念は常に同じ語で呼ぶ**。一度使った用語を別の表現に言い換えない
  (バリエーションを出すことに価値はなく、読む側の混乱にしかならない)。
- 用語は 2 層で管理する:共通の用語表記(技術用語の日本語表記ゆれの統一。
  例:「デプロイ」に統一し「デプロイメント」「配備」を使わない)と、
  プロジェクト用語集(各リポの CLAUDE.md。4.3 のコード語彙と同じ用語集に統合し、
  コード・ドキュメント・会話で共通に使う)。
- 新しい概念に名前が必要になったときは、勝手に名付けず用語集への追加として人間に提示する。

### 4.5 自然な日本語の文体規約(→ P13)

「AI 生成特有の不自然さ」を避ける文体規約を定める。抽象的な「自然に書け」では効かないため、
典型パターンの禁止リストとして具体化する(内容は次工程で確定。候補):

- 唐突な比喩・気取った修飾を使わない(「羅針盤のように」「〜という宝箱」等)
- 大げさな評価語を使わない(「劇的に」「飛躍的に」「強力な」「シームレスに」等)
- 翻訳調を避ける(「〜することができます」→「〜できます」、「〜を提供します」の乱用等)
- 見出し・箇条書き・絵文字の過剰使用を避け、普通の文章で説明する
- 文書種別ごとに文体(です・ます/だ・である)を固定し、混在させない
- 慣用的でないカタカナ語や聞き慣れない熟語を使わない
- **見出しは名詞句(体言止め)にし、文章を書かない**
  (×「テストを実行して結果を確認する」→ ○「テストの実行」)
- **太字の乱用をやめる**:強調は本当に立てたい語句だけに最小限使う。
  強調したい語そのものではなく間の文章が太字になっている「範囲のずれた強調」を作らない
- 規約には**良い例・悪い例の対比サンプル**を含める(禁止リストより例のほうが効くため)

### 4.6 ドキュメントの書き方(→ P7, P8, P14, P15, P16)

文書の層構成(3.7)に加えて、書き方の規約を定める:

- **形式の統一**:ドキュメントの種類ごとに標準の構成(テンプレート)を定め、
  どのリポジトリでも同じ形式で書く。
- **追記ではなく統合**:開発途中に受けた指示・決定をドキュメントに反映するときは、
  末尾や脚注に「追記」として貼り付けるのではなく、**本来あるべき場所に織り込み、
  最初からそう書かれていたかのように全体を再編集する**。
  更新後は文書全体を読み直し、一貫した品質になっていることを確認する。
- **履歴は git に任せる**:経緯・変更履歴を本文に残さない。
  「なお」「※後から追加」のような節を作らない。
- **図の使用基準**:3 つ以上の構成要素が相互に関係する構造(アーキテクチャ、AWS 構成)や、
  処理・データの流れ・状態遷移のように順序や分岐を持つものだけを図にする
  (単純な列挙・二者の関係・手順の説明は文章か表で足りる)。記法は原則 Mermaid
  (テキストで管理でき、GitHub 上でそのまま描画され、差分レビューできる)。
  本文を更新したのに図が古いまま残るのが最悪なので、更新時は図も再確認する。
- **表の使用ルール**:同種の項目を同じ属性で比較・列挙するときに使い、
  構造がないものを無理に表にしない。セルには短い名詞句・値だけを書き、文章を書かない。
  列見出しの用語は用語集(4.4)に従い、同じ種類の表は列構成も揃える。
- **GitHub 拡張記法の使い分け**:GitHub 上にだけ存在する文書(PR 説明・Issue・
  レビューコメント・返信)では GitHub Flavored Markdown の拡張記法(アラート、
  タスクリスト、折りたたみ、`#123` や commit SHA の自動リンク、suggestion ブロック等)を
  積極的に使う。リポジトリに格納する文書・コードでは環境依存の拡張記法を使わず、
  どの環境でも読める標準的な Markdown に留める。

### 4.7 確認・調査の方法論(→ P18)

確認・調査を依頼されたとき、思いつきで挙げるのではなく、次の手順に従う:

1. **観点の列挙**:何を確認すべきかの観点リストを先に作り、提示する
   (確認の種類ごとに標準の観点リストを規約側に用意し、タスク固有の観点を足す)。
2. **対象の列挙**:どこを調べるかの母集団(ファイル・モジュール・リソース)を明示する。
3. **突き合わせ**:観点 × 対象を突き合わせて確認する。見つかった問題は該当箇所付きで報告する。
4. **カバレッジの報告**:結果には「何を・どの範囲まで調べたか」「調べていない範囲」
   「漏れの可能性」を必ず含める。**指摘の一覧だけでなく、網羅の根拠を示す**。

この方法論は単発の確認依頼だけでなく、レビュー(3.1)や人間判断の監査(3.5)にも
共通で適用する。

### 4.8 不具合対応の方法論(→ P19)

不具合の修正では、症状を直して終わりにせず、次をセットで行う:

1. **根本原因の掘り下げ(なぜなぜ分析)**:症状 → 直接原因 → 根本原因まで
   「なぜ」を繰り返して掘り、その連鎖を修正報告に含める。対処は根本原因に対して行う
   (根本原因に手を入れない場合は、その判断理由を明示する)。
2. **横展開の確認**:同じ原因パターンによる不具合が他の箇所に埋め込まれていないかを、
   4.7 の方法論(観点 × 対象の突き合わせ)で網羅的に確認し、結果を報告する。
3. **再発防止**:再現テストの追加(4.1)に加えて、規約・チェックリスト側に反映すべき
   教訓があれば、用語集や観点リストへの追加として人間に提案する。

この方法論は、不具合起点の実装作業の手順に組み込む。

### 4.9 AWS リソースの命名・タグ規約(→ P11)

- リソース名の統一パターン(例:`{project}-{env}-{用途}` 形式)と、
  必須タグセット(例:`Project` / `Environment` / `ManagedBy`)を共通規約として定める。
- AWS は全プロジェクト共通の基盤なので、この規約はリポジトリ個別ではなく共通設定側に置く。
- **作成手段を問わず適用する**:CloudFormation・Terraform・CDK・AWS CLI・SDK・コンソール操作の
  いずれで作る場合でも、同じ命名・タグ規約に従う。規約はツール非依存の形
  (「何をどう名付け、どのタグを付けるか」)で定義し、特定 IaC の書式に依存させない。
- 具体的な命名パターン・タグ一覧の中身は次工程(実現手段の設計)で確定する。

## 5. やらないこと(非要件)

- マージ・リリース判断の自動化(むしろ禁止する側)
- 設計・仕様の決定の委任
- リポジトリ固有の情報(コマンド・注意点)を共通設定側に持つこと

## 6. スコープ外だが記録しておく課題

- 外出時に自宅マシンの電源を落とすため、出先からローカル作業ができない。
  AWS 認証が必要な作業を Web 版(クラウド実行環境への認証情報設定など)でも
  できるようにする件は、本件とは別課題として検討する。

## 7. 実現方針(次工程への申し送り)

実現手段の設計は次の方針で行う:

1. **運用モデル(3 節)を最優先で実装する**。役割別セッションの手順と定型書式 5 種は
   手動呼び出しのスキル(コマンド一発で書式と手順が読み込まれる形)とし、
   段取りと書式の毎回の手打ち(P2)をなくす。判断の 3 分類・書式の規律は
   AI が自動参照するスキルとする。PR・Issue・判断依頼のテンプレートは
   `.github/`(`PULL_REQUEST_TEMPLATE.md`・`ISSUE_TEMPLATE/`。判断依頼用テンプレートを
   含む)の配布物とし、人間が手で書くときも同じ形式に誘導されるようにする。
   ラベル 4 種(3.3)とブランチ保護(3.1)の設定は、新規リポジトリ立ち上げ手順に含める。
   レビューは同一セッション内のサブエージェントではなく、別セッションが PR 上で行う
   (運用モデルどおり。サブエージェント方式は採用しない)。
2. **「実装しない役割」はツールレベルで強制する**。指揮役・レビュー役が実装しないことは
   plan mode 等のツール側の仕組みで強制し、指示では頼まない。
3. **追加要件(4 節)は段階導入する**。一度に作り込まず、実際に破られた・困った順に導入し、
   有効性を確認できたものから運用モデルへ組み入れる。
4. **プロンプト/機械の仕分けを設計の最初のタスクにする**。各要件を
   「プロンプトで指示する(スキル・CLAUDE.md)」と「機械的に強制する
   (hooks・permissions・ブランチ保護・linter)」に仕分ける。
   毎回例外なく起きるべきことはプロンプトに頼らず機械側に落とす。
   例:TDD(4.1)はフックでのテスト実行、マージ禁止(3.1)は permissions とブランチ保護、
   用語・文体(4.4・4.5)は textlint 等の校正ツール+用語辞書、形式(4.6)は markdownlint。
5. **検証ループを中心に置く**。AI が自分で検証して直しきれる手段(テスト・lint・校正)を
   与え、「成功の主張」ではなくコマンド実行結果などの証拠を提示させる(3.5・4.7 と接続)。
6. **スタック非依存・Web 版ファーストにする**。共通設定に特定言語のコマンド
   (`npm test` 等)を書かず、各リポジトリの CLAUDE.md に書かれたコマンドを参照する
   方式にする。基本の作業場所が Web 版なので、Web 版セッションで確実に効く配布方法
   (プラグインマーケットプレイス+各リポジトリ用 settings.json / CLAUDE.md テンプレート)
   にし、ローカルにしか効かない仕組みに依存しない。
7. **常時ロードする規約を最小化する**。スキルは呼ばれたときだけ読み込まれる性質を活かし、
   CLAUDE.md・常駐規約は「消したらミスが起きるか」で選別する(3.7 の層構成とも整合)。
8. **既存資産を自作より先に調査する**。仕様駆動開発系のコマンド群(cc-sdd、spec-kit 等)、
   Claude Code 組み込みのレビュー機能、スケジュール実行(Routines)などで
   代替できる要件は自作しない。採否と理由を設計文書に残す。
9. **Web 版の技術的前提を設計時に検証する**。リモート実行判定、SessionStart フック、
   プラグインのバージョン更新の挙動などは、伝聞ではなく実際に動かして確認した上で
   構成を決める。
