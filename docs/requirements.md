# 要件定義書:個人開発のための Claude 共通設定(ドラフト v0.1)

> 状態:ドラフト。レビュー・赤入れ待ち。
> 目的:何を作るかを決める前に「何に困っていて、何を Claude に任せ、何を人間が握るか」を確定する。

## 1. 現状

- 複数リポジトリを個人開発している。スタックは AWS / Python / Node.js / Go(Go は自分では書かない=読解支援の重要度が高い)。
- Claude Code は基本 Web 版。ローカル環境や AWS 認証情報が必要な作業のみローカル CLI。
- 開発の進め方はセッション分業型:
  - **コーディングセッション**:実装 → PR 作成 → PR を購読してレビューコメントに対応
  - **レビューセッション**:別セッションが PR をレビューしてコメント → 解決まで追跡
  - つまり AI 同士が PR 上で作業を進め、人間は「判断」と「マージ」を担う。

## 2. 解決したい課題

| # | 課題 | 現状の症状 |
|---|------|-----------|
| P1 | 規約が実行時に守られない | TDD で開発すると規約に書いてあるのに、コード先行・テスト後書きになる |
| P2 | 定型セッションの段取りを毎回手打ちしている | コーディング/レビューセッションの手順(PR 作成 → 購読 → 対応ループ等)を毎回指示している |
| P3 | AI が人間の権限を越えることがある | たまに勝手にマージされる。マージは人間の判断にしたい |
| P4 | 人間判断の漏れを検証できない | 人間が判断すべき事項を AI 同士で勝手に決めて進めていないか、不安が残る |
| P5 | 判断を求められたときの説明が不親切 | コードやドキュメントを自分で探して参照しないと判断できない。毎回質問して説明させるのが面倒 |
| P6 | 理解が浅いまま着手する | 中途半端な理解のまま開発を始める。リポジトリ全体を確認せず一部だけの認識でコードを書いてきて、指摘する手間が発生する。求めてもいないファイルを作り始める |
| P7 | ドキュメントの形式がバラバラ | ものによって書き方・構成が違い、一貫性がない |
| P8 | 途中指示がドキュメントに「継ぎ足し」で残る | 開発途中に出した指示がそのまま追記され、木の節のように目立つ形で残る。本来はきれいな一貫した品質のドキュメントに織り込まれてほしい |
| P9 | Issue・PR の形式がバラバラ | 書かれ方が毎回違うので、読むたびに構造を把握し直す認知負荷がかかる |

## 3. 要件

### R1:定型セッションをコマンド一発で起動できる(→ P2)

- **コーディングセッション用コマンド**:タスクを受けて、TDD 手順で実装 → PR 作成 → PR を購読 → レビューコメント対応ループ → 「マージ可能な状態」で人間に引き渡して終了する。
- **レビューセッション用コマンド**:指定 PR をレビュー → 重要度分類付きでコメント → 解決まで追跡 → 承認・マージ判断は人間に委ねて終了する。

### R2:TDD を「規約」ではなく「手順」として強制する(→ P1)

- 「規約に書いておく」だけでは守られないことが実証済み。コーディング手順そのものに
  「(1) まず失敗するテストを書く →(2) 失敗することを確認 →(3) 実装 →(4) 通過を確認」
  を明示的なステップとして組み込む。
- 成果報告に「テストを先に書き、実装前に失敗を確認したか」を必須項目として含めさせる。

### R3:人間の専権事項を明文化する(→ P3, P4)

人間だけが行うこと:

1. **マージ**(およびリリースのタグ付け)
2. **機能の仕様・仕組みの最終決定**(AI は選択肢と論点を出し、議論相手にはなるが、決定はしない)
3. **リリース前の実動作確認**

- AI はこれらを代行しない。指示が曖昧でも勝手に踏み込まず確認を取る。
- 指示だけに頼らず技術的にも強制する:マージ系操作の権限拒否設定、GitHub ブランチ保護
  (人間の approve 必須)を併用する。

### R4:人間へのエスカレーションの品質を規定する(→ P4, P5)

判断を求めるときは、**その場で読むだけで判断できる自己完結フォーマット**を義務付ける:

- 何を決めてほしいか(1 行)
- 背景(なぜこの判断が必要になったか)
- 選択肢とそれぞれのトレードオフ
- 関連するコード・ドキュメントの**該当箇所の引用**(リンクだけ貼って調べさせない)
- AI としての推奨案と理由

さらに、セッション終了時(PR 引き渡し時)に
**「人間判断に委ねた事項の一覧/AI 側で判断した事項の一覧」** を報告させ、
「勝手に決めて進めていないか」を人間が監査できるようにする。

### R5:完了の定義を 2 段階にする

- **PR レベル**:テスト・lint・型チェックが通っていること+説明フォーマットの遵守。
- **リリースレベル(タグ付け時)**:人間による実動作確認が済んでいること。
  AI は確認手順とチェックリストを用意する役割。

### R6:スタック非依存・Web 版ファースト

- 共通設定に特定言語のコマンド(`npm test` 等)を書かない。
  各リポジトリの CLAUDE.md に書かれたコマンドを参照する方式にする。
- 基本の作業場所が Web 版なので、Web 版セッションで確実に効く配布方法にする。
  ローカルにしか効かない仕組みに依存しない。

### R7:着手前に「理解の確認」を必須にする(→ P6)

コードを書き始める前に、次を必ず行う:

1. **リポジトリ全体の把握**:関連コードだけでなく、全体構造・既存の類似実装・規約を確認する。
   一部だけ読んで書き始めない。
2. **理解の提示**:タスクの理解・影響範囲・進め方を短く提示し、認識がずれていれば
   ここで直せるようにする。理解に穴があるなら着手前に質問する。
3. **成果物の限定**:求められた成果物以外のファイルを勝手に作らない
   (「ついでに」の README・サンプル・スクリプト生成を禁止)。

### R8:ドキュメントの品質規約を定める(→ P7, P8)

- **形式の統一**:ドキュメントの種類ごとに標準の構成(テンプレート)を定め、
  どのリポジトリでも同じ形式で書く。
- **追記ではなく統合**:開発途中に受けた指示・決定をドキュメントに反映するときは、
  末尾や脚注に「追記」として貼り付けるのではなく、**本来あるべき場所に織り込み、
  最初からそう書かれていたかのように全体を再編集する**。
  更新後は文書全体を読み直し、一貫した品質になっていることを確認する。
- **履歴は git に任せる**:経緯・変更履歴を本文に残さない。
  「なお」「※後から追加」のような節を作らない。

### R9:Issue・PR のフォーマットを固定する(→ P9)

- Issue・PR それぞれに標準フォーマットを 1 つ定め、AI はどのリポジトリでも常に
  その形式で書く。**見慣れた形に統一することで、読む側(人間)の認知負荷を下げる**のが目的。
- GitHub 側のテンプレート(`.github/PULL_REQUEST_TEMPLATE.md`、`.github/ISSUE_TEMPLATE/`)も
  テンプレート集に含め、新規リポジトリ立ち上げ時に配布する。
  人間が手で書くときも同じ形式に誘導される。
- R4(エスカレーション形式)・R5(PR 説明形式)・R8(ドキュメント形式)と合わせて、
  「AI からの出力はすべて定型フォーマットで受け取る」を横断原則とする。

## 4. やらないこと(非要件)

- マージ・リリース判断の自動化(むしろ禁止する側)
- 設計・仕様の決定の委任
- リポジトリ固有の情報(コマンド・注意点)を共通設定側に持つこと

## 5. スコープ外だが記録しておく課題

- 外出時に自宅マシンの電源を落とすため、出先からローカル作業ができない。
  AWS 認証が必要な作業を Web 版(クラウド実行環境への認証情報設定など)でも
  できるようにする件は、本件とは別課題として検討する。

## 6. 実現手段の見取り図(参考。次工程で確定する)

| 要件 | 実現手段の候補 |
|------|--------------|
| R1 | 手動呼び出し専用のスキル(コーディングセッション用/レビューセッション用) |
| R2, R4, R5 | AI が自動参照するスキル(完了の定義・エスカレーション規約) |
| R3 | スキルでの明文化+permissions 設定+GitHub ブランチ保護の併用 |
| R6 | プラグインマーケットプレイスでの配布+各リポジトリ用 settings.json / CLAUDE.md テンプレート |
| R7 | コーディングセッション手順の冒頭に「着手前フェーズ」として組み込む |
| R8 | AI が自動参照するスキル(ドキュメント規約)+ドキュメント種類別テンプレート |
| R9 | Issue・PR の標準フォーマットをスキルに規定+`.github/` テンプレートを配布物に追加 |

※ 当初案にあった「同一セッション内で動くレビュー用サブエージェント」は、
実際の運用(別セッションが PR 上でレビューする)と合わないため採用しない。
