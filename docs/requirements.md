# 要件定義書:個人開発のための Claude 共通設定(ドラフト v0.2)

> 状態:ドラフト。レビュー・赤入れ待ち。
> v0.1 からの変更:別プロジェクトでの実運用により実証された運用知見(指揮役・文書の 4 層構造・人間判断の 3 分類・レビュー細則・課題管理の Issue 一本化・判断依頼の Issue 起票・定型書式 5 種)を反映した。
> 目的:何を作るかを決める前に「何に困っていて、何を Claude に任せ、何を人間が握るか」を確定する。

## 1. 現状

- 複数リポジトリを個人開発している。スタックは AWS / Python / Node.js / Go(Go は自分では書かない=読解支援の重要度が高い)。
- Claude Code は基本 Web 版。ローカル環境や AWS 認証情報が必要な作業のみローカル CLI。
- 開発の進め方はセッション分業型:
  - **指揮役セッション**:人間と直接やり取りする窓口。作業の範囲を定めて実装・レビューを
    別セッションへ依頼し、最後に人間へ報告する。自分では実装しない
  - **コーディングセッション**:実装 → PR 作成 → PR を購読してレビューコメントに対応
  - **レビューセッション**:別セッションが PR をレビューしてコメント → 解決まで追跡
  - つまり AI 同士が PR 上で作業を進め、人間は「判断」と「マージ」を担う。

## 2. 解決したい課題

| # | 課題 | 現状の症状 |
|---|------|-----------|
| P1 | 規約が実行時に守られない | TDD で開発すると規約に書いてあるのに、コード先行・テスト後書きになる |
| P2 | 定型セッションの段取りを毎回手打ちしている | コーディング/レビューセッションの手順(PR 作成 → 購読 → 対応ループ等)を毎回指示している |
| P3 | AI が人間の権限を越えることがある | たまに勝手にマージされる。マージは人間の判断にしたい |
| P4 | 人間判断の漏れを検証できない | 人間が判断すべき事項を AI 同士で勝手に決めて進めていないか、不安が残る |
| P5 | 判断を求められたときの説明が不親切 | コードやドキュメントを自分で探して参照しないと判断できない。毎回質問して説明させるのが面倒 |
| P6 | 理解が浅いまま着手する | 中途半端な理解のまま開発を始める。リポジトリ全体を確認せず一部だけの認識でコードを書いてきて、指摘する手間が発生する。求めてもいないファイルを作り始める |
| P7 | ドキュメントの形式がバラバラ | ものによって書き方・構成が違い、一貫性がない |
| P8 | 途中指示がドキュメントに「継ぎ足し」で残る | 開発途中に出した指示がそのまま追記され、木の節のように目立つ形で残る。本来はきれいな一貫した品質のドキュメントに織り込まれてほしい |
| P9 | Issue・PR の形式がバラバラ | 書かれ方が毎回違うので、読むたびに構造を把握し直す認知負荷がかかる |
| P10 | コード内の命名がばらつく・実態を表さない | 変数などの命名が実行ごとにばらつく。また「その名前ではコードの実態を表さないだろう」という命名をすることがある |
| P11 | AWS リソースの命名・タグに規則がない | リソース名やタグの付け方が統一されておらず、管理しづらい |
| P12 | 用語が定義されておらず、勝手に言い換えられる | 今まで使っていた用語を突然別の言い方で表現してくるので、同じものを指しているのか分からなくなる |
| P13 | AI 生成特有の不自然な日本語 | 突然、不自然な言い回しや使い慣れない比喩を使った文書を出してくる。自然な日本語で書くことを徹底したい。見出しに文章を書くのも嫌(日本語ではしない) |
| P14 | 図を入れる基準がない | アーキテクチャ・概念・AWS 構成などは図が適する場面で文章だけで説明される。かといって全てのケースで図が欲しいわけでもなく、入れる/入れないの基準がない |
| P15 | 表の形式が不統一 | 表形式で情報を並べるときの書き方にルールがなく、統一性がない |
| P16 | 記法の使い分けができていない | GitHub 上の文書(PR・Issue・コメント)では GitHub の拡張記法を活かせるのに使わない。一方でリポジトリに格納する文書に環境依存の記法を使われても困る |
| P17 | AI の対応コメントにルールがない | レビュー指摘などに AI が対応したとき、どんなコメントをどんな形式で残すかが決まっていない |
| P18 | 確認・調査が思いつきベース | 「問題となりうる箇所がないか確認して」と頼むと、仕組み的に網羅せず、思いついた一部だけを挙げてくる。何をどこまで調べたのかも分からない |
| P19 | 不具合対応が対症療法で終わる | 目の前の症状を直して終わりになりがち。根本原因の掘り下げ(なぜなぜ分析)や、同様の不具合が他に埋め込まれていないかの横展開確認をしてほしい |
| P20 | コード内コメントに規律がない | 何をコメントに書き、何を書かないかが決まっておらず、書き方・量がばらつく |
| P21 | 課題管理が二重になる | 作業中に気づいた課題の置き場が定まっておらず、リポジトリ内の課題台帳(CSV)と GitHub Issue の二重管理が実運用で発生した |

## 3. 要件

### R1:定型セッションをコマンド一発で起動できる(→ P2)

セッションは 4 種類に分け、それぞれコマンド一発で起動できるようにする:

- **設計セッション**:要件・設計を人間と議論することに専念するセッション。
  **実装やファイル作成は行わない**(勝手に書き始めることを構造的に防ぐ)。
  成果物は要件・設計ドキュメントで、**誰が見ても分かる水準で丁寧に書き、リポジトリに残す**。
  このドキュメントが次のコーディングセッションへの入力になる
  (セッションをまたぐ以上、口頭伝達はできないため、精度はドキュメントの質で担保する)。
- **指揮役セッション**:人間と直接やり取りする窓口となるセッション。
  作業の範囲(目的・範囲・範囲外・完了条件)を定めてコーディングセッションへ実装を、
  レビューセッションへレビューを依頼し、最後に人間へ報告して終了する。
  **自分では実装しない**(範囲を定めて監督する役と手を動かす役を分ける)。
  依頼と報告には定型書式(実装依頼・レビュー依頼・作業報告。R4・R9 参照)を使う。
- **コーディングセッション**:設計セッションの成果物や指揮役からの実装依頼を入力に、
  TDD 手順で実装 → PR 作成 → PR を購読 → レビューコメント対応ループ →
  「マージ可能な状態」で人間に引き渡して終了する。
- **レビューセッション**:指定 PR をレビュー → 「差し戻し/推奨/任意」の区分付きでコメント
  (区分の定義は R17)→ 解決まで追跡 → 承認・マージ判断は人間に委ねて終了する。
  レビューの入力は**対象 PR 番号と観点だけ**とし、実装役による説明は渡さない
  (変更の意図を先に読ませると、その説明と整合しているかを確かめるだけの
  形式的なレビューになるため)。レビュー役は原則 1 セッションとし、
  **後から取り消せない変更(R3 の分類 1)に関わる PR に限り 2 セッションに依頼する**。

### R2:TDD を「規約」ではなく「手順」として強制する(→ P1)

- 「規約に書いておく」だけでは守られないことが実証済み。コーディング手順そのものに
  「(1) まず失敗するテストを書く →(2) 失敗することを確認 →(3) 実装 →(4) 通過を確認」
  を明示的なステップとして組み込む。
- 成果報告に「テストを先に書き、実装前に失敗を確認したか」を必須項目として含めさせる。

### R3:人間の専権事項を明文化する(→ P3, P4)

人間だけが行うこと:

1. **マージ**(およびリリースのタグ付け)
2. **機能の仕様・仕組みの最終決定**(AI は選択肢と論点を出し、議論相手にはなるが、決定はしない)
3. **リリース前の実動作確認**

- AI はこれらを代行しない。指示が曖昧でも勝手に踏み込まず確認を取る。
- 指示だけに頼らず技術的にも強制する:マージ系操作の権限拒否設定、GitHub ブランチ保護
  (人間の approve 必須)を併用する。
- ブランチ保護は現在未導入。**本件のセットアップの一部として各リポジトリへ導入する**
  (導入手順をドキュメント化し、新規リポジトリ立ち上げ手順にも含める)。

これに加えて、**作業中に人間の判断を仰ぐ基準**を次の 3 分類で定める:

1. **後から取り消せない変更**:データの削除・上書き、稼働中の処理の挙動変更、
   外部への送信・公開の条件の変更など
2. **取り決めを変える変更**:合意済みの設計・規約・既決事項を実質的に変えることになる場合、
   規定どうしの矛盾に気づいた場合(どちらに合わせるかを独断で決めない)
3. **歯止めを緩める変更、費用や権限が増える変更**:テスト・CI の検査の削除・スキップ・緩和、
   費用の発生、権限や依存の拡大など

いずれにも該当しない事柄は、AI が自分で決めて進めるか、課題として起票して(R9)先へ進む。
判断がつかない場合も課題へ回す。
「判断すべきか迷ったら全部聞く」でも「全部自分で決める」でもなく、
この 3 分類との照合で機械的に振り分けられるようにするのが狙いである。

### R4:人間へのエスカレーションの品質を規定する(→ P4, P5)

判断を求めるときは、**その場で読むだけで判断できる自己完結フォーマット**(判断依頼)を
義務付ける:

- 何を決めてほしいか(1 行)
- R3 の 3 分類のどれに該当するか(該当しないものは判断依頼にせず、
  自分で決めるか課題として起票する)
- 背景(なぜこの判断が必要になったか)
- 選択肢とそれぞれのトレードオフ
- 関連するコード・ドキュメントの**該当箇所の引用**(リンクだけ貼って調べさせない)
- AI としての推奨案と理由
- 放置した場合に何が起きるか(期限の有無)

人間への報告は、1 行目に結論(人間が次に何をすればよいか)を置く定型書式(作業報告)で
統一する。判断を要する件がある場合は、別のメッセージに切り出さず、
作業報告の中に判断依頼の項目をそのまま埋め込む(報告と判断材料を 1 か所で読めるようにする)。

判断依頼は、報告の中に書くだけでなく **GitHub Issue としても起票する**。
報告文中にしか存在しない判断依頼は、セッションが終わった時点で忘れられうるうえ、
裁定待ちの全量を一覧できず、裁定の結果も証跡として残らない。
Issue に起票すれば、裁定待ちは Issue の一覧で追跡でき、裁定後のクローズが証跡になる
(課題管理を GitHub Issue に一本化する R9 とも揃う)。
上記の判断依頼フォーマットは Issue テンプレートとしても配布する(R9)。
裁定の記録先と、クローズの条件(誰がいつ閉じるか)も運用として定める
(具体化は次工程で行う)。

さらに、セッション終了時(PR 引き渡し時)に
**「人間判断に委ねた事項の一覧/AI 側で判断した事項の一覧」** を報告させ、
「勝手に決めて進めていないか」を人間が監査できるようにする。

この一覧は**セッションの出力ではなく、PR(説明欄またはコメント)に記録として残す**。
セッション自体は使い捨てで保存されないため、セッション内に出しても記録にならない。
永続する場所(PR・Issue・リポジトリ)に書かれて初めて事実として扱え、監査可能になる。

### R5:完了の定義を 2 段階にする

- **PR レベル**:テスト・lint・型チェックが通っていること+説明フォーマットの遵守。
- **リリースレベル(タグ付け時)**:人間による実動作確認が済んでいること。
  AI は確認手順とチェックリストを用意する役割。

### R6:スタック非依存・Web 版ファースト

- 共通設定に特定言語のコマンド(`npm test` 等)を書かない。
  各リポジトリの CLAUDE.md に書かれたコマンドを参照する方式にする。
- 基本の作業場所が Web 版なので、Web 版セッションで確実に効く配布方法にする。
  ローカルにしか効かない仕組みに依存しない。

### R7:着手前に「理解の確認」を必須にする(→ P6)

コードを書き始める前に、次を必ず行う:

1. **リポジトリ全体の把握**:関連コードだけでなく、全体構造・既存の類似実装・規約を確認する。
   一部だけ読んで書き始めない。
2. **理解の提示**:タスクの理解・影響範囲・進め方を短く提示し、認識がずれていれば
   ここで直せるようにする。理解に穴があるなら着手前に質問する。
3. **成果物の限定**:求められた成果物以外のファイルを勝手に作らない
   (「ついでに」の README・サンプル・スクリプト生成を禁止)。

### R8:ドキュメントの品質規約を定める(→ P7, P8)

- **4 層構造**:文書を「判断の基準(全セッションが最初に読む)/共通手順(手を動かす前に
  読む)/作業別手順(自分の作業に当たる 1 枚だけを読む)/正本=設計・規定の全文
  (必要な箇所だけを引く)」の 4 層に分ける。上の層ほど読む機会が多いため、薄く保つ。
  **上の層に下の層の内容や正本への参照を書かない**。上の層に正本への参照を書くと、
  全セッションが正本を開くことになり、自分の作業と関係のない規定を読むことに時間を使う。
  参照は、それを必要とする層に置く。
- **実装状態を正本に書かない**:「未着手」「後続 PR で対応」のような実装状態を
  設計・規定の文書に持ち込まない。状態を持つのは課題管理(R9 の GitHub Issue)だけとする。
- **形式の統一**:ドキュメントの種類ごとに標準の構成(テンプレート)を定め、
  どのリポジトリでも同じ形式で書く。
- **追記ではなく統合**:開発途中に受けた指示・決定をドキュメントに反映するときは、
  末尾や脚注に「追記」として貼り付けるのではなく、**本来あるべき場所に織り込み、
  最初からそう書かれていたかのように全体を再編集する**。
  更新後は文書全体を読み直し、一貫した品質になっていることを確認する。
- **履歴は git に任せる**:経緯・変更履歴を本文に残さない。
  「なお」「※後から追加」のような節を作らない。

### R9:Issue・PR のフォーマットを固定し、課題管理を GitHub Issue に一本化する(→ P9, P21)

- Issue・PR それぞれに標準フォーマットを 1 つ定め、AI はどのリポジトリでも常に
  その形式で書く。**見慣れた形に統一することで、読む側(人間)の認知負荷を下げる**のが目的。
- **課題管理は GitHub Issue に一本化する**:作業中に気づいた範囲外の課題は、
  その場で手をつけず Issue へ起票して先へ進む。リポジトリ内に CSV 等の課題台帳を持たない
  (台帳と Issue の二重管理が実運用で発生したため。同じ課題を 2 か所に書く手間と、
  どちらが最新か分からなくなる問題を、置き場を 1 つにすることで断つ)。
  人間の判断を要する事項も同様に Issue で扱い(R4 の判断依頼)、
  **人間が追うべきものの置き場を GitHub Issue の 1 か所にする**。
- GitHub 側のテンプレート(`.github/PULL_REQUEST_TEMPLATE.md`、`.github/ISSUE_TEMPLATE/`)も
  テンプレート集に含め、新規リポジトリ立ち上げ時に配布する。
  Issue テンプレートには課題用に加えて判断依頼用(R4 のフォーマット)を含める。
  人間が手で書くときも同じ形式に誘導される。
- R4(エスカレーション形式)・R5(PR 説明形式)・R8(ドキュメント形式)と合わせて、
  「AI からの出力はすべて定型フォーマットで受け取る」を横断原則とする。
  定型書式は**実装依頼・レビュー依頼・指摘・判断依頼・作業報告の 5 種**とし
  (実装依頼・レビュー依頼・作業報告は R1、判断依頼は R4、指摘は R17)、
  いずれも実運用で有効性を確認済みである。

### R10:コード内の命名を「原則+リポジトリ語彙」で統一する(→ P10)

コードごとに中身が違う以上、完全な統一ルールは作れない。そこで 2 層で対応する:

- **共通の命名原則**(プラグイン側):言語横断で通用する原則を定める。例:
  - 名前は役割・内容を表す(処理の実態と食い違う名前を付けない)
  - boolean は `is/has/can` 等、関数は動詞句、定数・環境変数は大文字スネーク等の一般慣習
  - **新しい名前を導入する前に、既存コードで同じ概念に使われている語を探し、それに合わせる**
    (同じ概念に別の語を増やさない)
- **リポジトリ固有の語彙**(各リポの CLAUDE.md):そのプロジェクトのドメイン用語集
  (この概念はこの単語で呼ぶ)を書き、命名時に参照させる。
- 「命名が実態を表しているか」をレビュー(レビューセッション)の明示的な観点に含める。

### R11:AWS リソースの命名・タグ規約を定める(→ P11)

- リソース名の統一パターン(例:`{project}-{env}-{用途}` 形式)と、
  必須タグセット(例:`Project` / `Environment` / `ManagedBy`)を共通規約として定める。
- AWS は全プロジェクト共通の基盤なので、この規約はリポジトリ個別ではなく共通設定側に置く。
- **作成手段を問わず適用する**:CloudFormation・Terraform・CDK・AWS CLI・SDK・コンソール操作の
  いずれで作る場合でも、同じ命名・タグ規約に従う。規約はツール非依存の形
  (「何をどう名付け、どのタグを付けるか」)で定義し、特定 IaC の書式に依存させない。
- 具体的な命名パターン・タグ一覧の中身は次工程(実現手段の設計)で確定する。

### R12:用語を定義し、言い換えを禁止する(→ P12)

- **同じ概念は常に同じ語で呼ぶ**。一度使った用語を別の表現に言い換えない
  (バリエーションを出すことに価値はなく、読む側の混乱にしかならない)。
- 用語は 2 層で管理する:
  - **共通の用語表記**(共通設定側):技術用語の日本語表記ゆれの統一
    (例:「デプロイ」に統一し「デプロイメント」「配備」を使わない、など)。
  - **プロジェクト用語集**(各リポの CLAUDE.md):そのプロジェクトのドメイン用語。
    R10 のコード語彙と同じ用語集に統合し、コード・ドキュメント・会話で共通に使う。
- 新しい概念に名前が必要になったときは、勝手に名付けず用語集への追加として人間に提示する。

### R13:自然な日本語で書くことを徹底する(→ P13)

「AI 生成特有の不自然さ」を避ける文体規約を定める。抽象的な「自然に書け」では効かないため、
典型パターンの禁止リストとして具体化する(内容は次工程で確定。候補):

- 唐突な比喩・気取った修飾を使わない(「羅針盤のように」「〜という宝箱」等)
- 大げさな評価語を使わない(「劇的に」「飛躍的に」「強力な」「シームレスに」等)
- 翻訳調を避ける(「〜することができます」→「〜できます」、「〜を提供します」の乱用等)
- 見出し・箇条書き・絵文字の過剰使用を避け、普通の文章で説明する
- 文書種別ごとに文体(です・ます/だ・である)を固定し、混在させない
- 慣用的でないカタカナ語や聞き慣れない熟語を使わない
- **見出しは名詞句(体言止め)にし、文章を書かない**
  (×「テストを実行して結果を確認する」→ ○「テストの実行」)
- **太字の乱用をやめる**:強調は本当に立てたい語句だけに最小限使う。
  特に、強調したい語そのものではなく間の文章が太字になっている「範囲のずれた強調」を作らない
- 規約には**良い例・悪い例の対比サンプル**を含める(禁止リストより例のほうが効くため)

### R14:図の使用基準と記法を定める(→ P14)

- **図を入れる基準**を定める。全てのケースに図は不要。候補となる基準:
  - 3 つ以上の構成要素が相互に関係する構造(アーキテクチャ、AWS 構成)
  - 処理の流れ・データの流れ・状態遷移など、順序や分岐を持つもの
  - 逆に、単純な列挙・二者の関係・手順の説明は文章か表で足りるので図にしない
- **記法・ツールを統一する**:リポジトリ内ドキュメントの図は原則 Mermaid
  (テキストで管理でき、GitHub 上でそのまま描画され、差分レビューできるため)。
  AWS 構成図の表現方法(Mermaid で足りるか、別ツールを使うか)は次工程で決める。
- 図もドキュメントの一部として R8 の「追記ではなく統合」に従う。
  **本文を更新したのに図が古いまま残るのが最悪**なので、更新時は図も再確認する。

### R15:表の使用ルールを定める(→ P15)

- **表を使う条件**:同種の項目を同じ属性で比較・列挙するときに使う。
  構造がないものを無理に表にしない。逆に該当する場合は文章で羅列しない。
- **セルの書き方**:セルには短い名詞句・値だけを書き、文章を書かない。
  説明が必要なら本文に書く。
- 列見出しの用語は用語集(R12)に従う。同じ種類の表は列構成も揃える。
- 詳細ルールと見本は次工程でドキュメントテンプレート(R8)の一部として定める。

### R16:GitHub 拡張記法の使い分けを定める(→ P16)

- **GitHub 上にだけ存在する文書**(PR 説明・Issue・レビューコメント・返信)では、
  GitHub Flavored Markdown の拡張記法を積極的に使う。
  例:アラート(`> [!NOTE]` / `> [!WARNING]` 等のラベル表示)、タスクリスト
  (`- [ ]`)、折りたたみ(`<details>`)、`#123` や commit SHA の自動リンク、
  レビューでの suggestion ブロック。
- **リポジトリに格納する文書・コード**では、GitHub 依存の拡張記法を使わない。
  格納物はどの環境でも読める標準的な Markdown に留める。
- どの記法をどちらで使ってよいかの一覧を規約に含める。

### R17:レビュー指摘と対応コメントのルールを定める(→ P17)

レビュー指摘の書き方と、指摘・Issue などに AI が対応したときに残すコメントの形式を定める。
骨子:

- **指摘の区分**:レビュー指摘(定型書式「指摘」)には次のいずれかを付ける。
  区分がないと、どこまで対応すればマージできるのかを人間が毎回判断することになる。
  - **差し戻し**:明確な不具合・検証の不備・R3 の判断基準に該当するもの。対応するまでマージしない
  - **推奨**:直したほうがよいが、直さなくても動くもの。対応の要否は実装役が判断し、
    直さない場合は課題として起票する(R9)
  - **任意**:好みの範囲にとどまるもの。対応しなくてよい
- **やり取りの上限**:指摘 1 件についての実装役とレビュー役のやり取りは最大 2 往復とし、
  解消しない指摘は保留として人間へ回す(AI 同士の押し問答で時間を消費させない)。
- **対応した場合**:何をどう変えたか(1〜2 行)+対応コミットへの参照を書く。
  「修正しました」だけの中身のないコメントを禁止する。
- **対応しない場合**:必ず理由を書く(見送りの判断根拠、代替案)。無言で放置しない。
- **判断を人間に委ねる場合**:R4 のエスカレーション形式に従う。
- 指摘スレッドの解決(resolve)を誰がするか(対応した AI か、確認した人間か)も定める。

### R18:確認・調査の方法論を定める(→ P18)

確認・調査を依頼されたとき、思いつきで挙げるのではなく、次の手順に従う:

1. **観点の列挙**:何を確認すべきかの観点リストを先に作り、提示する
   (確認の種類ごとに標準の観点リストを規約側に用意し、タスク固有の観点を足す)。
2. **対象の列挙**:どこを調べるかの母集団(ファイル・モジュール・リソース)を明示する。
3. **突き合わせ**:観点 × 対象を突き合わせて確認する。見つかった問題は該当箇所付きで報告する。
4. **カバレッジの報告**:結果には「何を・どの範囲まで調べたか」「調べていない範囲」
   「漏れの可能性」を必ず含める。**指摘の一覧だけでなく、網羅の根拠を示す**。

この方法論は単発の確認依頼だけでなく、レビューセッション(R1)や
人間判断の監査(R4)にも共通で適用する。

### R19:不具合対応の方法論を定める(→ P19)

不具合の修正では、症状を直して終わりにせず、次をセットで行う:

1. **根本原因の掘り下げ(なぜなぜ分析)**:症状 → 直接原因 → 根本原因まで
   「なぜ」を繰り返して掘り、その連鎖を修正報告に含める。対処は根本原因に対して行う
   (根本原因に手を入れない場合は、その判断理由を明示する)。
2. **横展開の確認**:同じ原因パターンによる不具合が他の箇所に埋め込まれていないかを、
   R18 の方法論(観点 × 対象の突き合わせ)で網羅的に確認し、結果を報告する。
3. **再発防止**:再現テストの追加(R2)に加えて、規約・チェックリスト側に反映すべき
   教訓があれば、用語集や観点リストへの追加として人間に提案する。

この方法論は不具合修正セッション(R1 のコーディングセッションのうち不具合起点のもの)に
組み込む。

### R20:コード内コメントの規約を定める(→ P20)

コードに書くコメントの規律を定める(詳細は次工程で確定。候補):

- コードを読めば分かることを書かない(処理の逐語説明の禁止)。
  書くのは**コードから読み取れないこと**:意図、制約、そうした理由、既知の落とし穴。
- 変更の経緯・作業説明(「〜を修正」「レビュー指摘対応」等)をコードに残さない。
  経緯は git・PR が持つ(R8 の「履歴は git に任せる」と同じ原則)。
- 公開 API・関数のドキュメントコメントは、言語ごとの標準慣習
  (docstring、JSDoc、godoc 等)に従う。
- コメントの言語(日本語/英語)の方針を定める。

## 4. やらないこと(非要件)

- マージ・リリース判断の自動化(むしろ禁止する側)
- 設計・仕様の決定の委任
- リポジトリ固有の情報(コマンド・注意点)を共通設定側に持つこと

## 5. スコープ外だが記録しておく課題

- 外出時に自宅マシンの電源を落とすため、出先からローカル作業ができない。
  AWS 認証が必要な作業を Web 版(クラウド実行環境への認証情報設定など)でも
  できるようにする件は、本件とは別課題として検討する。

## 7. 実現方針(次工程への申し送り)

要件は v0.1 時点で P1〜P20 として凍結した。以降の追加は「実運用で実際に困った実例」が
出たときに行う(v0.2 の改訂と P21 の追加は、この方針に基づくものである)。
外部レビューで得た指摘を踏まえ、実現手段の設計は次の方針で行う:

1. **プロンプト/機械の仕分けを設計の最初のタスクにする**。
   R1〜R20 の各要件を「プロンプトで指示する(スキル・CLAUDE.md)」と
   「機械的に強制する(hooks・permissions・ブランチ保護・linter)」に仕分ける。
   毎回例外なく起きるべきことはプロンプトに頼らず機械側に落とす。
   例:TDD(P1)はフックでのテスト実行、マージ禁止(P3)は permissions とブランチ保護、
   文体・用語(P12/P13)は textlint 等の校正ツール+用語辞書、形式(P7/P15)は markdownlint。
2. **検証ループを中心に置く**。AI が自分で検証して直しきれる手段(テスト・lint・校正)を
   与え、「成功の主張」ではなくコマンド実行結果などの証拠を提示させる(R4・R18 と接続)。
3. **設計セッションの実装禁止はツールレベルで強制する**(plan mode 等。指示で頼まない)。
4. **常時ロードする規約を最小化する**。スキルは呼ばれたときだけ読み込まれる性質を活かし、
   CLAUDE.md・常駐規約は「消したらミスが起きるか」で選別する。
5. **段階導入**。20 要件を一度に作り込まず、実際に破られた規約から順に機械側へ落とす。
6. **既存資産を自作より先に調査する**。仕様駆動開発系のコマンド群(cc-sdd、spec-kit 等)、
   Claude Code 組み込みのレビュー機能、スケジュール実行(Routines)などで
   代替できる要件は自作しない。採否と理由を設計文書に残す。
7. **Web 版の技術的前提を設計時に検証する**。リモート実行判定、SessionStart フック、
   プラグインのバージョン更新の挙動などは、伝聞ではなく実際に動かして確認した上で
   構成を決める。
